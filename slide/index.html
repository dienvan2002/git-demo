Trước 2005: Thời đại BitKeeper

Linux Kernel — dự án mã nguồn mở lớn nhất thế giới — dùng BitKeeper, một phần mềm kiểm soát phiên bản độc quyền & thương mại. Cộng đồng được dùng miễn phí theo thoả thuận đặc biệt.

Khủng hoảng: BitKeeper Thu Hồi Giấy Phép

BitMover (công ty sau BitKeeper) thu hồi giấy phép miễn phí sau khi phát hiện thành viên cộng đồng reverse-engineer giao thức của họ. Toàn bộ cộng đồng Linux bị khoá khỏi hệ thống quản lý source code!

⚡

Giải pháp: Linus Tự Viết Git

Linus Torvalds quyết định tự xây dựng hệ thống mới. Chỉ trong vài tuần, phiên bản đầu tiên của Git ra đời. Ngày 7 tháng 4 năm 2005 — commit đầu tiên được tạo ra!

Tiêu chí thiết kế của Linus:   Phân tán (DVCS)   Siêu nhanh   Phi tuyến tính   Toàn vẹn dữ liệu   Mã nguồn mở

🏆 5 Lý Do Git Là Công Cụ Bắt Buộc

🌐 Kiến Trúc Phân Tán (DVCS)

Mỗi developer có toàn bộ lịch sử dự án ngay trên máy mình. Làm việc offline hoàn toàn — commit, branch, merge không cần internet. Server chỉ là điểm đồng bộ.

⚡ Tạo Nhánh Siêu Nhẹ

Branch trong Git chỉ là một file 41 bytes chứa con trỏ SHA. Tạo & chuyển nhánh trong mili-giây. Tạo bao nhiêu branch tuỳ thích, không tốn tài nguyên.

🔒 Toàn Vẹn Dữ Liệu

Mọi commit, file, tree đều được checksum bằng SHA-1 / SHA-256. Không ai có thể thay đổi lịch sử commit mà không bị phát hiện ngay lập tức.

🎯 Staging Area Độc Đáo

Vùng trung gian cho phép chọn lọc chính xác thay đổi nào sẽ vào commit. Dùng git add -p để commit từng hunk — commit mạch lạc, dễ review.

🚑 Khả Năng Phục Hồi Vô Song

reflog — revert — reset — cherry-pick  →  Git luôn có cứu hộ cho mọi sự cố. Gần như không có gì bị mất vĩnh viễn trong 30 ngày đầu.

Snapshot, Hash, HEAD & Detached HEAD

📸 Commit Là "Ảnh Chụp" (Snapshot), Không Phải Bản Vá

❌ SVN / CVS

Lưu danh sách thay đổi
(Diff / Delta)

✅ GIT

Lưu toàn bộ trạng thái
(Snapshot)

Hash SHA-1/SHA-256: Mỗi commit = chuỗi 40 ký tự duy nhất, tính từ: Nội dung code + Metadata + Hash của commit cha.  →  Commit là BẤT BIẾN (Immutable) — "Sửa commit" = tạo commit mới với Hash hoàn toàn mới!

🗂️ Bức Tranh 4 Vùng Làm Việc

🧭 Con Trỏ HEAD & Trạng Thái Detached HEAD

✅ HEAD Bình Thường

HEAD → branch → commit. Khi bạn tạo commit mới, branch label tự động tiến lên.

⚠️ Detached HEAD

HEAD trỏ thẳng vào commit, không qua branch. Commit trong trạng thái này có thể bị mất.

# Gây ra Detached HEAD
git checkout abc1234

# Xem trạng thái
git status
HEAD detached at abc1234

# Thoát — Bỏ thay đổi
git checkout main

# Thoát — Giữ thay đổi thành branch mới
git checkout -b hot-fix
⚠️ Cảnh Báo Quan Trọng:
Nếu bạn commit trong Detached HEAD và checkout sang branch khác → commit đó sẽ BỊ MẤT (garbage collected sau ~30 ngày)! Hãy luôn tạo branch mới trước khi commit.
💡 Trường hợp hữu ích: Detached HEAD rất có ích khi bạn muốn kiểm tra code cũ mà không tạo branch. Chỉ cần đọc, không commit thì hoàn toàn an toàn.

Merge, Rebase, Reset, Cherry-pick & Worktree

🔀 Fast-Forward vs --no-ff: Khi Nào Dùng Gì?

Fast-Forward (mặc định) --no-ff (khuyên dùng)
Lịch sử Thẳng tắp, sạch sẽ Có merge commit, rõ ràng
Truy vết Khó biết tính năng nào đâu Dễ thấy từng feature branch
Revert Khó (không có điểm rõ ràng) Dễ: git revert <merge-commit>
Khuyên dùng Merge cá nhân, local cleanup ✅ Merge PR vào main/develop 
# Merge với --no-ff (tạo merge commit)
git merge feature/login --no-ff -m "merge: feature login vào develop"

# Xem graph lịch sử đẹp
git log --oneline --graph --all

⚔️ git merge vs git rebase — Hiểu Đúng Để Không Hối Hận

git merge git rebase
Lịch sử Giữ nguyên, có merge commit Viết lại thành đường thẳng
Conflict Giải quyết 1 lần duy nhất Có thể giải quyết từng commit
An toàn ✅ Luôn an toàn ⚠️ KHÔNG dùng trên nhánh đã push
Dùng khi Merge feature vào main/develop Cập nhật feature branch từ main
🚫 GOLDEN RULE: Không bao giờ rebase branch đã được push lên remote và người khác đang sử dụng! Vì rebase viết lại history → gây ra diverged branch cho mọi người. 
# ✅ Cập nhật feature branch từ main (an toàn với rebase)
git checkout feature/my-feature
git rebase main

# ✅ Pull sạch — không tạo merge commit thừa
git pull --rebase origin main

# Nếu có conflict khi rebase
# Giải quyết conflict rồi:
git add .
git rebase --continue   # tiếp tục
# Hoặc:
git rebase --abort      # huỷ toàn bộ rebase

💣 git reset — 3 Cấp Độ Uy Lực

Lệnh Working Directory Staging Area Commit History Dùng Khi
--soft ✅ Giữ nguyên ✅ Giữ nguyên 🔄 Xoá commit Muốn gộp lại commit, sửa message
--mixed (default) ✅ Giữ nguyên ❌ Xoá khỏi stage 🔄 Xoá commit Muốn stage lại cẩn thận hơn
--hard ❌ XOÁ VĨNH VIỄN ❌ Xoá khỏi stage 🔄 Xoá commit Muốn xoá hoàn toàn, không cần giữ
☠️ Nguy Hiểm: git reset --hard sẽ XOÁ VĨNH VIỄN các thay đổi chưa commit trong Working Directory. Hãy chắc chắn 100% trước khi dùng! Nếu lỡ tay, dùng git reflog để khôi phục. 
git reset --soft  HEAD~1   # Bỏ commit, giữ code trong staging area
git reset --mixed HEAD~1   # Bỏ commit, giữ code trong working directory
git reset --hard  HEAD~1   # ☠️ Bỏ commit VÀ xoá code (cực nguy hiểm!)
git reset --hard  HEAD~3   # ☠️ Xoá 3 commit gần nhất và toàn bộ code

🛠️ Cherry-pick, Worktree & Tag

🍒 git cherry-pick

Lấy đúng 1 (hoặc nhiều) commit từ nhánh khác, áp dụng vào nhánh hiện tại mà không merge toàn bộ nhánh.

# Lấy 1 commit cụ thể
git cherry-pick abc1234

# Lấy nhiều commit
git cherry-pick abc1234 def5678

# Lấy dải commit
git cherry-pick abc..def

# Chỉ stage, chưa commit
git cherry-pick -n abc1234

💡 Dùng khi: Hotfix cần áp dụng lên nhiều branch, hoặc lấy 1 commit fix bug từ nhánh khác.

🌳 git worktree

Làm việc với 2 nhánh song song trong cùng lúc, không cần stash. Mỗi worktree là 1 thư mục riêng biệt.

# Tạo worktree mới cho hotfix
git worktree add ../hotfix hotfix/urgent

# Xem tất cả worktrees
git worktree list

# Làm xong → dọn dẹp
git worktree remove ../hotfix

💡 Dùng khi: Đang code feature dở dang, cần chạy sang fix bug gấp mà không muốn commit code chưa xong.

🏷️ git tag

Đánh dấu release version cụ thể trong lịch sử. Tag không di chuyển như branch — nó gắn chặt vào 1 commit.

# Tạo annotated tag (khuyên dùng)
git tag -a v1.0.0 -m "Release v1.0.0"

# Xem tất cả tags
git tag -l

# Push tags lên remote
git push origin --tags

# Xoá tag
git tag -d v1.0.0
git push origin :refs/tags/v1.0.0

GitHub Flow · Conventional Commits · Tự Động Hoá

👥 Quy Trình Làm Việc Nhóm Chuẩn Mực

6 Bước Quy Trình
1
git checkout develop && git pull --rebase origin develop
2
git checkout -b feature/ten-tinh-nang
3
Code... git add -p → git commit -m "feat: thêm chức năng X"
4
git push origin feature/ten-tinh-nang
5
Tạo Pull Request → Code Review với team
6
Merge vào develop (sau khi approved) với --no-ff
💡 Tip: Dùng git add -p để commit từng phần thay đổi. Commit nhỏ, rõ ràng = review nhanh hơn!
Branch Naming Convention
feature/ Tính năng mới
bugfix/ Sửa lỗi thông thường
hotfix/ Fix khẩn trên production
release/ Chuẩn bị release
chore/ Bảo trì, CI/CD

✍️ Conventional Commits — Viết Commit Message Chuyên Nghiệp

<type>(<scope>): <description>
Type Dùng Khi Ví Dụ
feat Thêm tính năng mới feat(auth): thêm đăng nhập Google
fix Sửa bug fix(cart): sửa lỗi tính tổng tiền
docs Cập nhật tài liệu docs(readme): thêm hướng dẫn setup
style Format, không đổi logic style: format theo prettier
refactor Tái cấu trúc code refactor(api): tách service layer
test Thêm/sửa test test(login): thêm unit test
chore Bảo trì, dependencies chore: update dependencies
💡 Tại sao quan trọng?
Commit message tốt = tài liệu tự động cho team. git log --oneline sẽ đẹp như thơ! Và các tool như Semantic Release có thể tự động tạo CHANGELOG & bump version. 
# Xem log đẹp
git log --oneline --graph

# Output mẫu:
* feat(auth): thêm đăng nhập Google
* fix(cart): sửa lỗi tính tổng tiền
* docs: cập nhật README
* chore: update dependencies
Breaking change: Thêm ! sau type: feat(api)!: thay đổi response format → tự động tạo major version.

🪝 Git Hooks — Tự Động Hoá Kiểm Soát Chất Lượng

pre-commit

🖥️ Chạy trên máy local

Chạy linter & formatter trước khi commit. Từ chối commit nếu code xấu, chưa đúng chuẩn.

commit-msg

🖥️ Chạy trên máy local

Kiểm tra format commit message. Từ chối nếu không theo Conventional Commits.

pre-push

🖥️ Chạy trên máy local

Chạy test suite trước khi push. Chặn push nếu có test fail — không push code hỏng!

pre-receive

☁️ Chạy phía server

Kiểm tra phía server. Từ chối push vi phạm policy — tuyến phòng thủ cuối cùng.

Setup với Husky + lint-staged (Node.js) 
# Cài Husky — tự động manage git hooks
npx husky-init && npm install

# Thêm pre-commit hook: chạy lint-staged
npx husky add .husky/pre-commit "npx lint-staged"

# Thêm commit-msg hook: kiểm tra conventional commits
npx husky add .husky/commit-msg "npx commitlint --edit $1"

# Thêm pre-push hook: chạy tests
npx husky add .husky/pre-push "npm test"

7 Tình Huống Thực Chiến
& Cứu Nguy Sự Cố

Từ Merge Conflict Đến Rò Rỉ Secret — Không Tình Huống Nào Phải Hoảng Loạn

🔥 Các Tình Huống Thực Chiến (1–4)

😱 1. Lỡ Commit Vào Nhánh Sai

git reset --soft HEAD~1 # lấy lại commit → staged
git stash              # cất tạm code
git checkout correct-branch
git stash pop          # lấy code ra
git commit -m "feat: ..."

💥 2. Merge Conflict Không Giải Quyết Được

git merge feature/abc    # conflict!
# Mở file, sửa conflict markers:
# <<<<<<< HEAD  ... =======  ... >>>>>>>
git add .
git commit -m "merge: resolve conflict"
# Hoặc huỷ toàn bộ merge:
git merge --abort

📦 3. Pull Giữ Lịch Sử Sạch

# ❌ Tạo merge commit thừa
git pull origin main

# ✅ Pull sạch, không merge commit
git pull --rebase origin main

# Cấu hình mặc định
git config --global pull.rebase true

⚠️ 4. Đồng Đội Force Push, Branch Bị Lệch

git fetch origin
git reset --hard origin/feature/abc
# ☠️ Mất code local!

# Khôi phục bằng reflog:
git reflog
git checkout -b recovery <hash>

💡 Luôn dùng git reflog trước khi panic!

🆘 Các Tình Huống Thực Chiến (5–7) & Phao Cứu Sinh reflog

🧹 5. Gộp Commit Lộn Xộn

Squash nhiều "WIP" commit thành 1 commit sạch trước khi merge PR.

# Interactive rebase
git rebase -i HEAD~4

# Trong editor, đổi:
# 'pick' → 's' (squash)
# để gộp vào commit trước

🕵️ 6. Lỡ reset --hard, Muốn Lấy Lại

Code "mất" sau reset --hard thực ra vẫn còn trong reflog!

# Xem toàn bộ lịch sử HEAD
git reflog

# Tìm hash trước khi reset
# Tạo branch từ commit đó
git checkout -b recovery abc1234

🔑 7. Lỡ Push Secret/Token

Secret trong git history = PUBLIC. Phải hành động ngay!

# B1: Thu hồi token NGAY TRÊN PROVIDER!
# B2: Xoá khỏi git history
git filter-repo --path .env --invert-paths
git push origin --force --all
# B3: Thêm vào .gitignore
echo ".env" >> .gitignore
🆘 git reflog — Phao Cứu Sinh Cuối Cùng

git reflog ghi nhận MỌI thao tác di chuyển HEAD, kể cả reset --hard, checkout, rebase.  →  Không có gì thực sự mất trong Git cho đến khi garbage collection chạy (~30 ngày). Khi hoảng loạn, hãy luôn chạy git reflog trước!
